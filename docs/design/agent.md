# Agent 与知识库架构（设计稿 v2.1 §3）

---

## 3. Agent 与知识库架构（套用你笔记里的分层）

### 3.1 一次对话的流程

```
用户消息
  → Gateway（Cloudflare Pages Function）：Turnstile、配额（共享存储）、长度上限
  → Agent 服务：
      a. 安全分词：用户 / 工具 / 知识文本一律禁用特殊 token 解析；
         控制 token 与 Gist id 只由 prompt 层按 id 插入
      b. 代码预处理：正则抽出订单号、邮箱（确定性字段代码读，不让模型猜）
      c. 组装 prompt = [固定前缀：完整规则 或 Gist token] + 对话历史 + 用户消息
      d. 模型输出：要么直接回答，要么发 tool call
      e. 代码校验 tool call 参数：订单号 / 邮箱必须是用户真的说过的，否则追问
      f. 执行工具，返回类型化结果 Found | NotFound | Mismatch | UpstreamError：
         先校验、后读缓存；切换订单需重新校验，并清除前一单的事实
      g. 工具结果作为 <tool_response> 回给模型 → 模型组织回答
      h. 来源核查：答案里所有数字 / 日期 / 相对时间词必须出现在本轮工具结果、
         用户消息或知识命中中，否则替换为安全回复，raw / final 各记一次
  → 返回：回答 + public 投影；internal 投影写入 trace
```

> **大白话 · 特殊 token**：模型内部有一些“暗号”，比如“系统指令开始”。我们实测发现：如果用户输入里直接写这个暗号，分词器会把它当成真暗号，等于用户冒充了系统。所以所有用户、工具、知识库来的文字都按“纯文字”处理，真暗号只能由我们自己的代码按编号插入。

> **大白话 · 类型化结果**：查订单有四种结局：查到了、没这个订单、邮箱不对、上游出错。代码内部必须分得清（才能正确统计和排查），但对用户只说同一句“没找到匹配的订单”，让坏人分不出来。

### 3.2 知识放哪里（按你笔记第 4 节的判断法）

| 知识形态 | 本项目的例子 | 放哪里 | Gisting 能不能压缩 |
|---|---|---|---|
| 规则 | 不得编造日期；未发货不能说已发货；不泄露别人订单；何时转人工 | 固定前缀（system prompt） | **能**，这是 Gisting 的主要对象 |
| 知识地图 | 生产 3 个 tool（lookup_order、handoff_to_human、send_shipping_reminder）的名字、用途、参数说明；search_policy 不在其中 | 固定前缀里独立的工具段，两种模式都原文送入 | **不能**（Gist 只替换规则段；工具段随规则一起冻结，改了就要重训） |
| 人设/语气/格式 | 简短、友好、英文 | 固定前缀 | **能** |
| 结构化事实 | 订单状态、承运商、运单号、预计到达 | Shopify，经 lookup_order 精确查 | 不能（每次都不同） |
| 语义文本 | 配送时效、延误怎么办、退货政策、改地址 | 小型知识库，经 search_policy 检索；首发休眠（见 ADR 0009），生产不开放，模型发出的 search_policy 调用按 unknown_tool 处理 | 不能（每次检索结果不同） |

- 知识库规模：约 20–40 条短 FAQ/政策，一条 FAQ = 一个 chunk，带 metadata（id、category、version、valid_from、source）。
- 检索（首发休眠，代码与知识库保留）：这个规模下 **BM25 足够**，不上向量库；接口按“可替换为混合检索”设计，将来扩展不用改 Agent。
- 店铺是虚构的 “Gisting Lab Store”，政策由我们编写并标明是演示内容。

> **大白话（最重要的一条）**：Gisting 只压缩“每次都一模一样的那段开场白”里的规则段（员工手册）；同样固定的工具说明书照原文送入，不被压缩。每次都不一样的东西（这单的物流、刚检索到的政策段落）没法提前训练进去，只能原样给模型看。所以 Gisting 的收益 = 开场白有多长 × 每天聊多少轮。

### 3.3 和“前缀缓存”的关系：三臂对照 + 手工压缩基线

只拿 Gist 和“无缓存的完整规则”比，会放大 Gisting 的优势。v2 的对照至少有三臂，再加一条手工基线：

| 臂 | 做法 | 回答的问题 |
|---|---|---|
| A. Full | 每轮都送完整规则，不缓存 | 最朴素的基准 |
| B. Full + 前缀缓存 | 完整规则的计算结果缓存复用 | 不训练、只靠工程手段能省多少 |
| C. Gist | 固定规则换成十几个 Gist token | Gisting 在 B 之上还多给了什么（内存、并发、缓存放不下的场景） |
| 基线 D. 同等预算手工压缩提示 | 人手把规则压缩到与 Gist 相同的 token 预算 | 学出来的压缩是否真的比“认真写短”更好 |

- 页面和报告里“节省”一词必须写明是相对哪一臂；页面上会话累计与计算器里的反事实节省固定是**相对 A**。
- Full 提示要做**规则消融**：逐块删掉规则，证明每块都对红线或质量有贡献，没有往里注水。往完整规则里灌水会让“节省比”虚高，这是被审查指出的口径漏洞（F9）。
- KV cache 字节数不再作为 gate，只作展示；效率指标用 transcripts 重放计算（见第 7 节）。

> **大白话**：想证明“新发明的压缩衣更省地方”，不能只拿“摊开的大衣箱”比，还要和“真空压缩袋”（前缀缓存）比，再和“自己认真叠一遍”（手工压缩）比。三个都比过，结论才站得住。
